## 1. Краткое резюме (TL;DR)

Для QuantumForge Software предлагается **local-first гибридная конфигурация**: чувствительные документы обрабатываются полностью внутри контура компании, а для заведомо публичных/внутренних материалов допускается облачный fallback.

| Слой | Рекомендация | Ключевая причина |
|---|---|---|
| LLM | **Qwen2.5-32B-Instruct (AWQ, vLLM)** + GPT-4o-mini как fallback для неконфиденциального трафика; 8B-модель для маршрутизации и простых FAQ | Лучший баланс «качество / стоимость / конфиденциальность» для русского и английского языков, открытые веса, работа on-prem |
| Эмбеддинги | **BAAI/bge-m3** (1024 измерения, 8k контекст, мультиязычная) | Сильное качество на RU/EN и коде, поддержка dense + sparse (гибридный поиск), нулевая стоимость за токены |
| Векторное хранилище | **FAISS** (`IndexIDMap2` + `IndexFlatIP`, отдельные индексы по доменам доступа) | Точный поиск по 50–100 тыс. чанков за единицы миллисекунд, нет отдельного сервиса, полностью локально, простой Docker |
| Реранкер | **bge-reranker-v2-m3** | Заметно повышает точность top-k и качество цитирования |
| Сервер (prod) | **16 vCPU / 64 GB RAM / 1×NVIDIA L40S 48 GB (или A100 40 GB) / 1 TB NVMe** | 32B-модель в 4-bit + эмбеддинги + реранкер + FAISS с запасом по VRAM и RAM |
| Сервер (dev) | 8 vCPU / 32 GB RAM / 1×RTX 4090 24 GB (или CPU + облачный API) | Достаточно для разработки и приёмки |
| Развёртывание | Docker Compose (MVP), Kubernetes — при масштабировании | Соответствует требованиям проектной работы и не переусложняет первый релиз |

**Итог по векторной БД:** для бота выбирается **FAISS**. При объёме ~50 тыс. чанков (и до ~100 тыс. через год) он даёт точный поиск за миллисекунды, не требует отдельного сервера и полностью укладывается в контур компании. ChromaDB остаётся удобным инструментом для прототипа и локальных экспериментов, но в production добавляет лишний сервис, не давая выигрыша в качестве на нашем объёме. При росте до 0,5–1 млн векторов или при необходимости сложной фильтрации прав в реальном времени планируется миграция на **Qdrant**.

## 2. Контекст и требования

### 2.1. Кто даёт задачу и для кого она делается

| Стейкхолдер | Интерес | Метрика успеха |
|---|---|---|
| CTO / CPO | Снижение стоимости поиска знаний, масштабируемая платформа | Экономия FTE, стоимость ответа, возможность тиражирования |
| Руководитель Knowledge Management | Качество и актуальность базы знаний | Доля ответов с цитатами, найденные пробелы в документации |
| GRC / Security | Соответствие SOC 2, GDPR, отсутствие утечек | Отсутствие инцидентов, прохождение аудита, ≤ 40 ч на подготовку вместо 140 ч |
| Лиды поддержки и разработки | Разгрузка от повторяющихся вопросов | Deflection rate, снижение повторных обращений |
| HR / onboarding | Быстрый ввод новичков | Время до первого самостоятельного ответа |
| Сотрудники (4 основные роли) | Быстрый и точный ответ | Время ответа, доля ответов «не знаю» без галлюцинаций |

Бот делается **для сотрудников**, а не для внешних клиентов на первом этапе. Это важно: уровень доверия, требования к приватности и допустимая задержка отличаются от клиентского чат-бота.

### 2.2. Функциональные требования

- Ответ на естественно-языковой вопрос с **обязательными ссылками на источники** (файл, страница Confluence, раздел PDF).
- Персонализация по роли: разработчик, саппорт, менеджер/аналитик, новичок.
- Разграничение доступа: сотрудник не должен получать фрагменты документов, к которым у него нет прав.
- Режим «я не знаю»: если релевантность ниже порога, бот честно сообщает об отсутствии информации и предлагает зафиксировать пробел.
- Сбор обратной связи и логов для выявления пробелов в документации.
- Работа с RU и EN, с Markdown/MDX, Confluence, PDF.

### 2.3. Нефункциональные требования

| Требование | Целевое значение |
|---|---|
| Время ответа p95 | ≤ 8–10 с локально, ≤ 5 с в облачном варианте |
| Доступность | 99,5% для MVP, 99,9% при тиражировании |
| Актуальность индекса | Инкрементальное обновление ≤ 1 ч, полная переиндексация ночью |
| Конфиденциальность | Данные не покидают ЕС; секреты и restricted-документы — только on-prem |
| Аудируемость | Лог запросов, выданных источников и версий документов |
| Стоимость | ≤ €0,02 за ответ в локальном контуре (без учёта ФОТ) |

### 2.4. Оценка объёма данных

Оценка сделана по статистике из брифа и типовым размерам страниц. Точные цифры нужно уточнить на реальном корпусе.

| Источник | Объём | Средний размер | Оценка токенов |
|---|---:|---:|---:|
| Markdown/MDX в репозиториях | 18 000 файлов | ~4 КБ текста | ~16 млн |
| Confluence | 3 000 страниц | ~3 КБ текста | ~2 млн |
| PDF-спецификации | 250 документов × ~40 страниц | ~2 КБ текста/стр. | ~6 млн |
| **Итого стартовый корпус** | **~21 250 документов** | | **~24–26 млн токенов** |
| Прирост | 400 страниц/мес. | ~1 000 токенов/стр. | ~0,4–0,5 млн токенов/мес. |

При чанковании 600–800 токенов с перекрытием 10–15% получается:

- **~40–55 тыс. чанков** на старте;
- **~700 чанков/мес.** прироста, то есть **~60 тыс. чанков через год**;
- с учётом версий, дублей и переиндексации разумно проектировать систему **на 100–200 тыс. векторов**.

Размер индекса при 1024 измерениях и `float32`:

- 50 тыс. векторов ≈ 205 МБ «сырых» векторов;
- с ID, метаданными и overhead HNSW — **0,3–0,7 ГБ**;
- 200 тыс. векторов — **1,5–2,5 ГБ**, что свободно помещается в RAM одного сервера.

**Вывод:** задача по современным меркам небольшая. Она не требует распределённой векторной БД и укладывается в один узел. Это ключевой аргумент в пользу простых решений (FAISS / Chroma) вместо Milvus или Qdrant Cluster на старте.

### 2.5. Главное ограничение — конфиденциальность

В базе знаний есть:

- Terraform state и Helm charts (инфраструктура, потенциальные секреты);
- ADR и CODEOWNERS (архитектура, зоны ответственности);
- политики SOC 2, данные аудита, сведения о клиентах (ABB, Wärtsilä);
- внутренние регламенты и HR-документы.

Компания работает в ЕС и подпадает под GDPR. Передача таких данных в облачный API за пределы ЕС требует DPIA, DPA и юридической оценки, а для части документов может быть запрещена внутренней политикой. YandexGPT и GigaChat размещают данные в РФ, что для финско-эстонской компании создаёт неприемлемый регуляторный риск (отсутствие адекватного решения о защите данных).

Поэтому архитектура должна поддерживать **классификацию данных и маршрутизацию запросов**:

| Класс | Примеры | Где обрабатывается |
|---|---|---|
| Public | маркетинговые материалы, публичная документация | локально или облако |
| Internal | большинство Markdown, onboarding | локально по умолчанию, облако — опционально |
| Confidential | ADR, architecture decision records, клиентские интеграции | только локально |
| Restricted | Terraform state, SOC 2-доказательства, HR | только локально, отдельный индекс и ACL |

## 3. Методика сравнения и допущения

Сравнение ведётся по критериям задания, с весами для итогового решения:

| Критерий | Вес | Комментарий |
|---|---:|---|
| Качество ответов / поиска | 30% | Accuracy, groundedness, качество на RU и EN |
| Конфиденциальность и комплаенс | 25% | Возможность не выносить данные, GDPR, SOC 2 |
| Стоимость владения (TCO) | 20% | API + инфраструктура + ФОТ на эксплуатацию |
| Простота развёртывания и поддержки | 15% | Количество сервисов, требования к MLOps |
| Масштабируемость | 10% | Путь до 1 млн+ векторов и мультитенантности |

**Допущения по нагрузке:**

- 1 000 запросов в день, 22 рабочих дня → **22 тыс. запросов/мес.**;
- на запрос: ~3 000 входных токенов (контекст + вопрос + системный промпт) и ~400–500 выходных;
- месячный объём: **~66 млн входных и ~11 млн выходных токенов**;
- индексация: 25 млн токенов однократно + ~0,5 млн токенов/мес.

Цены на API и железо — ориентировочные, на момент подготовки документа; перед закупкой их нужно перепроверить у поставщиков. Оценки качества моделей — экспертные, на основе публичных бенчмарков (MMLU-Pro, Arena-Hard, MERA для русского, MTEB для эмбеддингов) и должны быть подтверждены замером на собственном golden set.

### 4.2. Качество ответов

Оценки по пятибалльной шкале (экспертно, до замеров на корпусе):

| Модель | Русский | Английский | Код и технические тексты | Следование инструкциям | Итог |
|---|---:|---:|---:|---:|---:|
| GPT-4o | 4,5 | 5,0 | 4,5 | 5,0 | **4,8** |
| GPT-4o-mini | 4,0 | 4,5 | 4,0 | 4,5 | **4,3** |
| YandexGPT 5 Pro | 4,5 | 3,5 | 3,5 | 4,0 | **3,9** |
| Qwen2.5-32B-Instruct | 4,5 | 4,5 | 4,5 | 4,5 | **4,5** |
| Llama 3.3 70B | 4,0 | 4,5 | 4,0 | 4,5 | **4,3** |
| Mistral Small 3.1 24B | 4,0 | 4,5 | 4,0 | 4,0 | **4,1** |
| Qwen2.5-7B | 3,5 | 3,5 | 3,5 | 3,5 | **3,5** |

Комментарии:

- **GPT-4o** — эталон качества, но дорог и выносит данные наружу; для restricted-документов неприемлем.
- **GPT-4o-mini** — лучший облачный вариант по соотношению цена/качество; хорош как fallback для public/internal.
- **YandexGPT 5 Pro** — сильный русский, но слабее в английском и коде, а главное — данные размещаются в РФ. Для QuantumForge это дисквалифицирующий фактор.
- **Qwen2.5-32B** — лучший открытый компромисс: уверенно работает с RU/EN, кодом и таблицами, хорошо следует формату ответа с цитатами. На 4-bit квантовании почти не теряет качество.
- **Llama 3.3 70B** — качество выше 32B, но требует 1×H100 80GB или 2×A100 80GB, что удваивает стоимость инфраструктуры. Разумный апгрейд второго этапа.
- **Mistral Small 3.1 24B** — эффективная альтернатива, но уступает Qwen на русском.
- **Qwen2.5-7B** — не для финальных ответов, а для маршрутизации, классификации запросов, переписывания query и простых FAQ.

### 4.3. Скорость работы

| Модель | TTFT | Генерация | Комментарий |
|---|---:|---:|---|
| GPT-4o | 0,3–0,8 с | 60–100 ток./с | Зависит от сети и загрузки API |
| GPT-4o-mini | 0,2–0,6 с | 80–120 ток./с | Самый быстрый облачный вариант |
| YandexGPT 5 Pro | 0,5–1,5 с | 30–60 ток./с | Зависит от региона и квот |
| Qwen2.5-32B AWQ, A100/L40S | 0,3–0,8 с | 35–60 ток./с | 300–500 токенов ответа ≈ 6–10 с |
| Llama 3.3 70B AWQ, H100 | 0,5–1,0 с | 20–35 ток./с | 300–500 токенов ≈ 10–20 с |
| Qwen2.5-7B, RTX 4090 | 0,2–0,5 с | 90–140 ток./с | Быстрые ответы на простые вопросы |
| Mistral Small 24B, L40S | 0,3–0,7 с | 50–80 ток./с | Хорошая скорость |

Для RAG-бота важна не только скорость генерации, но и **время до первого токена**: пользователь воспринимает систему как быструю, если ответ начинает появляться через 1–2 с. Поэтому потоковая выдача (streaming) обязательна.

Практический приём: **маршрутизация по сложности**. Простые FAQ и вопросы «где найти документ» отдаём 7–8B-модели, сложные аналитические вопросы — 32B. Это снижает среднюю задержку и нагрузку на GPU.

### 4.4. Стоимость владения и использования

Расчёт на 22 тыс. запросов/мес. (66 млн входных + 11 млн выходных токенов):

| Вариант | Переменные затраты | Постоянные затраты | Итого в месяц (ориентир) |
|---|---:|---:|---:|
| GPT-4o | ~$165 вход + ~$110 выход = **~$275** | нет | **~$275** + хостинг |
| GPT-4o-mini | ~$10 + ~$7 = **~$17** | нет | **~$17** + хостинг |
| YandexGPT 5 Pro | сопоставимо с GPT-4o-mini / GPT-4o в зависимости от версии | нет | уточнять; главный риск — юрисдикция |
| Qwen2.5-32B, свой GPU | электричество ~€50–100 | GPU-сервер €700–1 200 | **€750–1 300** |
| Llama 3.3 70B, свой GPU | электричество ~€80–150 | H100-сервер €1 800–3 000 | **€1 900–3 150** |
| Qwen2.5-7B, RTX 4090 | электричество ~€30–60 | сервер €300–500 | **€330–560** |

Что важно учесть в TCO локального варианта:

- **ФОТ на эксплуатацию.** Даже 0,2–0,3 FTE MLOps/DevOps — это €2 000–4 000/мес. Если команда уже есть, маржинальные затраты ниже, но совсем без людей локальный контур не живёт.
- **Пики нагрузки.** GPU оплачивается постоянно, даже ночью. API — только за фактические запросы.
- **Скрытые затраты API:** ретраи, рост контекста, эксперименты, повторная индексация, оценка качества. Легко получить ×2–3 к расчётной сумме.
- **Стоимость эмбеддингов** на фоне LLM пренебрежимо мала (см. раздел 5).

**Вывод по стоимости:** при текущем объёме облачный API дешевле локального GPU в 5–15 раз. Но экономия не является главной целью проекта: на кону конфиденциальность и комплаенс. Локальный контур окупается не «токенами», а снижением риска утечки и возможностью обрабатывать restricted-документы.

### 4.5. Удобство и простота развёртывания

| Модель | Развёртывание | Сложность | Что нужно |
|---|---|---|---|
| GPT-4o / GPT-4o-mini | API-ключ, SDK | ★☆☆☆☆ | Аккаунт, DPA, контроль расходов |
| YandexGPT / GigaChat | API-ключ, SDK | ★★☆☆☆ | Аккаунт в РФ-облаке, юридическая оценка |
| Qwen2.5-32B | vLLM/TGI в Docker | ★★★☆☆ | GPU, драйверы, квантование, мониторинг |
| Llama 3.3 70B | vLLM, tensor parallel | ★★★★☆ | 2×GPU или H100, больше VRAM и ops |
| Qwen2.5-7B | Ollama/vLLM | ★★☆☆☆ | Одна GPU 16–24 ГБ |

Для локальных моделей рекомендуется **vLLM**: он даёт continuous batching, PagedAttention, OpenAI-совместимый API и высокую пропускную способность. Это позволяет позже заменить модель или добавить вторую без переписывания приложения.

### 4.6. Вывод по LLM

- Для **restricted/confidential** — только локальная модель: **Qwen2.5-32B-Instruct AWQ** на vLLM.
- Для **public/internal** — допустим **GPT-4o-mini** как fallback или для сравнения качества.
- **YandexGPT/GigaChat** не подходят из-за размещения данных в РФ.
- **Llama 3.3 70B** — кандидат на второй этап, если качества 32B не хватит.
- **Qwen2.5-7B** — вспомогательная модель для маршрутизации и простых запросов.

> На момент подготовки документа также доступна **Qwen3-32B** (Apache 2.0). Её стоит включить в сравнительный замер на пилоте: при сопоставимой стоимости она может дать прирост качества и лучшую работу с рассуждениями. Версии моделей быстро меняются, поэтому в отчёте зафиксирован baseline, а финальная модель выбирается по результатам golden set.

### 5.2. Скорость создания индекса

Расчёт для 50 тыс. чанков (~25 млн токенов):

| Модель | Где считается | Время индексации | Комментарий |
|---|---|---:|---|
| bge-m3 | GPU L40S/A100 | **10–30 мин** | 500–1 500 чанков/с в зависимости от батча и длины |
| bge-m3 | CPU 8–16 ядер | 6–12 ч | Приемлемо для ночной переиндексации, но не для интерактива |
| multilingual-e5-large | GPU | 8–25 мин | Короткий контекст 512 токенов |
| multilingual-e5-base | GPU | 3–10 мин | Быстрее, но качество ниже |
| OpenAI text-embedding-3-small | API | 30–60 мин | Ограничения rate limit, сеть, батчи по 2 048 входов |
| OpenAI text-embedding-3-large | API | 40–90 мин | Медленнее и дороже, но всё ещё приемлемо |
| Yandex embeddings | API | 30–90 мин | Зависит от квот |

Важно: при обновлении базы знаний переиндексовывать весь корпус не нужно. Инкрементальная индексация 700 новых чанков в месяц занимает секунды на GPU и минуты на CPU. Полная переиндексация нужна только при смене модели эмбеддингов или схемы чанкования.

### 5.3. Качество поиска

Оценки на основе публичных лидербордов (MTEB, MIRACL RU) и ожиданий для корпуса QuantumForge:

| Модель | Русский | Английский | Код/Markdown | Ожидаемый Recall@10 | Комментарий |
|---|---:|---:|---:|---:|---|
| bge-m3 | 4,5 | 4,5 | 4,5 | 0,85–0,92 | Лучший открытый мультиязычный выбор, dense + sparse |
| multilingual-e5-large | 4,5 | 4,0 | 4,0 | 0,83–0,90 | Хорош на RU, короче контекст |
| multilingual-e5-base | 4,0 | 3,5 | 3,5 | 0,78–0,86 | Дешевле и быстрее, но заметно слабее |
| jina-embeddings-v3 | 4,5 | 4,5 | 4,0 | 0,84–0,91 | Нужна коммерческая лицензия |
| text-embedding-3-small | 4,0 | 4,5 | 4,0 | 0,82–0,89 | Дёшево, хорошо для EN, но данные уходят |
| text-embedding-3-large | 4,5 | 5,0 | 4,5 | 0,86–0,93 | Лучшее качество в облаке, дороже и внешнее |
| Yandex embeddings | 4,5 | 3,5 | 3,0 | 0,82–0,89 | Русский сильный, но юрисдикция РФ |

Ключевые факторы качества для нашего кейса:

- **Мультиязычность.** Запрос может быть на русском, а документ — на английском (и наоборот). bge-m3 и e5-large это поддерживают.
- **Длина контекста.** PDF-спецификации и большие Confluence-страницы выигрывают от 8k контекста, но мы всё равно режем на чанки 600–800 токенов.
- **Код и таблицы.** Markdown с кодом и таблицами — слабое место многих эмбеддингов; bge-m3 и OpenAI large справляются лучше.
- **Гибридный поиск.** bge-m3 умеет выдавать sparse-векторы (аналог BM25), что позволяет объединить semantic и lexical search и заметно улучшить поиск точных терминов: `Kafka`, `Terraform`, `SOC 2`, названий сервисов.

### 5.4. Стоимость владения и использования

| Модель | Стоимость индексации 25 млн токенов | Стоимость 0,5 млн токенов/мес. | Инфраструктура |
|---|---:|---:|---|
| bge-m3 | ~€0 (свой GPU) или €1–2 за час аренды GPU | ~€0 | GPU уже нужен для LLM |
| e5-large | ~€0 | ~€0 | GPU уже нужен |
| text-embedding-3-small | **~$0,50** | ~$0,01 | нет |
| text-embedding-3-large | **~$3,25** | ~$0,07 | нет |
| Yandex embeddings | уточнять | уточнять | нет, но данные в РФ |

Стоимость эмбеддингов настолько мала, что **не является решающим фактором**. Даже самый дорогой облачный вариант — это единицы долларов в месяц. Решают качество на нашем корпусе, конфиденциальность и отсутствие внешних зависимостей.

### 5.5. Вывод по эмбеддингам

- **Основной выбор: bge-m3.** Причины: мультиязычность, 8k контекст, поддержка sparse для гибридного поиска, отсутствие платы за токены, работа on-prem, сильные результаты на русском.
- **Резервный/сравнительный вариант: text-embedding-3-large** — используем только на этапе оценки качества и только для public/internal корпуса.
- **e5-large** — хорошая запасная локальная модель, если bge-m3 по каким-то причинам не подойдёт.
- **jina-v3** — не выбираем из-за лицензии.
- **Yandex embeddings** — не выбираем из-за юрисдикции.

## 6. Сравнение векторных хранилищ: FAISS и ChromaDB

### 6.1. Что это и как устроено

**FAISS** (Facebook AI Similarity Search) — библиотека для ANN-поиска, а не сервер. Работает in-process внутри Python-приложения, поддерживает Flat, IVF, HNSW, PQ, GPU-индексы. Индекс — это файл, который приложение сохраняет и загружает. Метаданные, ACL и версионирование нужно хранить отдельно (например, в PostgreSQL или SQLite).

**ChromaDB** — векторная БД с двумя режимами: embedded (`PersistentClient`, SQLite + HNSW) и client-server (отдельный сервис). Умеет хранить документы, метаданные и коллекции, поддерживает фильтрацию `where`, встроенные функции эмбеддингов. Это ближе к «готовой БД», чем FAISS.

Дополнительно рассматривались как путь масштабирования:

- **Qdrant** — серверная векторная БД с богатой фильтрацией, снапшотами, репликацией, multi-tenancy.
- **pgvector** — расширение PostgreSQL; удобно, если Postgres уже есть, но на 100k+ векторов требует более аккуратной настройки и уступает специализированным решениям при сложной фильтрации и масштабировании.
- **Milvus** — распределённая система для миллионов/миллиардов векторов; для нашего объёма избыточна.

### 6.2. Скорость поиска и индексации

Оценки для 50–100 тыс. векторов, 1024 измерения, один узел:

| Параметр | FAISS Flat | FAISS HNSW | Chroma embedded | Chroma server |
|---|---:|---:|---:|---:|
| Построение индекса 50k | 1–5 с | 10–60 с | 30–120 с | 1–3 мин |
| Поиск top-10, p50 | 3–10 мс | < 1 мс | 2–5 мс | 5–15 мс |
| Поиск top-10, p95 | 10–20 мс | 2–5 мс | 10–20 мс | 20–50 мс |
| Память на 100k | ~0,4 ГБ | ~0,6–0,8 ГБ | ~0,8–1,2 ГБ | ~1–1,5 ГБ + сервис |
| Фильтрация по метаданным | вручную / по ID | ограниченно | есть (`where`) | есть (`where`) |
| Обновление/удаление | ограниченно | ограниченно | есть | есть |
| Горизонтальное масштабирование | нет | нет | нет (Chroma Cloud отдельно) | нет |

На нашем объёме **оба варианта укладываются в требования по скорости**. Разница в единицы миллисекунд не влияет на пользовательский опыт, потому что основное время тратится на LLM (секунды). Поэтому скорость не должна быть главным критерием выбора.

### 6.3. Сложность внедрения и поддержки

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Компоненты | библиотека в приложении | библиотека или отдельный сервис |
| Docker | один контейнер бота | бот + Chroma (в server-режиме) |
| Персистентность | `write_index` / `read_index`, свой бэкап | встроенная, SQLite + сегменты |
| CRUD | нет полноценного; нужен ID-map и перестройка | есть add/update/delete |
| Метаданные и ACL | хранить отдельно, фильтровать по ID | встроены, фильтрация `where` |
| Авторизация | нет (на уровне приложения) | в server-режиме есть токены/базовая auth |
| Репликация и HA | нет | нет (в OSS-версии) |
| Наблюдаемость | метрики приложения | метрики приложения + сервиса |
| Кривая обучения | низкая для базового использования | очень низкая |
| Зависимости | `faiss-cpu` / `faiss-gpu` | `chromadb` + SQLite |

**FAISS** проще в смысле «нет лишнего сервиса», но требует самостоятельно реализовать слой метаданных и ACL. **ChromaDB** удобнее «из коробки», но добавляет сервис, бэкапы и обновления.

### 6.4. Удобство в работе

| Сценарий | FAISS | ChromaDB |
|---|---|---|
| Быстрый прототип | нужно написать обвязку | **очень удобно**: collections, metadata, документы |
| Хранение текста и метаданных | отдельно | **встроено** |
| Фильтрация по правам/пространствам | вручную, через отдельные индексы или по списку ID | **удобно** через `where` |
| Тонкая настройка индекса | **богатая**: Flat, IVF, HNSW, PQ, GPU | ограниченная (HNSW по умолчанию) |
| Контроль над результатом | **полный** | ниже, много «магии» |
| Отладка поиска | прозрачно | требует понимания внутренних коллекций |
| Воспроизводимость | **высокая** (файл индекса) | высокая, но зависит от версии |
| Экосистема LangChain | **есть** (`FAISS` vectorstore) | **есть** (`Chroma` vectorstore) |

Для команды, которая делает первого RAG-бота, ChromaDB снижает порог входа. Для команды, которой важны контроль, предсказуемость и минимум сервисов, FAISS удобнее в эксплуатации.

### 6.5. Стоимость владения

| Статья | FAISS | ChromaDB |
|---|---|---|
| Лицензия | MIT, бесплатно | Apache 2.0, бесплатно |
| Дополнительный сервис | нет | ~0,5–1 ГБ RAM, 1 vCPU в server-режиме |
| Диск | файл индекса | SQLite + сегменты + логи |
| Бэкап | копирование файла | согласованный бэкап БД |
| Обслуживание | обновление библиотеки | обновление библиотеки/сервера, миграции |
| Managed-вариант | нет (только self-host) | Chroma Cloud (платно) |
| Скрытые затраты | разработка слоя метаданных и ACL | эксплуатация сервиса и его обновлений |

На нашем объёме оба варианта **дешёвы**. Разница — не в деньгах, а в том, где вы платите сложностью: FAISS — разработкой обвязки, Chroma — эксплуатацией ещё одного сервиса.

### 6.6. Вывод по векторной БД

**Выбираем FAISS.** Аргументы:

1. **Объём мал.** 50–100 тыс. чанков — это «ноутбучный» масштаб. `IndexFlatIP` даёт точный (не приближённый) поиск за 3–10 мс, а HNSW — менее 1 мс. Приближённые структуры и распределённая БД не нужны.
2. **Ноль дополнительной инфраструктуры.** FAISS живёт внутри контейнера бота. Это упрощает Docker Compose, бэкапы, обновления и снижает число точек отказа.
3. **Полный контроль и воспроизводимость.** Файл индекса можно версионировать, пересобрать, сравнить. Для аудита и разбора инцидентов это плюс.
4. **Конфиденциальность.** Всё локально, нет сетевого сервиса, который нужно отдельно защищать и патчить.
5. **Достаточная функциональность при правильной архитектуре.** ACL реализуются через **отдельные индексы по доменам доступа** (engineering, support, business/GRC, onboarding/HR); в качестве альтернативы возможна предфильтрация по списку разрешённых ID на уровне приложения. Метаданные (source, owner, updated_at, classification, version) хранятся в PostgreSQL; при поиске сначала определяется домен, затем ищется по нужному индексу.
6. **Простой путь миграции.** Если корпус вырастет до 0,5–1 млн векторов или появится требование real-time ACL и мультитенантности, переходим на **Qdrant** (или pgvector, если нужен минимум сервисов). Абстракция vector store в LangChain позволяет заменить бэкенд без переписывания логики.

**Почему не ChromaDB сейчас:**

- На нашем объёме она не даёт выигрыша в скорости или качестве, но добавляет сервис и бэкапы.
- Встроенная фильтрация удобна, но ACL через отдельные индексы решает ту же задачу проще и безопаснее.
- OSS-версия не даёт HA и горизонтального масштабирования; при росте всё равно придётся мигрировать.

**Где ChromaDB всё же уместна:** локальные эксперименты, быстрый прототип, демонстрация заказчику, сравнение качества поиска. Мы можем использовать её на этапе исследования, но production-контур строим на FAISS.

## 7. Рекомендуемая конфигурация сервера

### 7.1. Что нужно посчитать

| Компонент | Ресурс | Расчёт |
|---|---|---|
| LLM 32B в 4-bit | VRAM | ~18–20 ГБ весов + 4–8 ГБ KV-кэш на 8k контекста → **24–28 ГБ** |
| Эмбеддинги bge-m3 | VRAM/CPU | ~2–3 ГБ VRAM или 2–4 ГБ RAM на CPU |
| Реранкер bge-reranker-v2-m3 | VRAM/CPU | ~2–3 ГБ VRAM или 2–4 ГБ RAM |
| FAISS-индекс | RAM | 0,3–0,8 ГБ на 50–100 тыс. векторов |
| Приложение, БД, очередь | RAM/CPU | 4–8 ГБ RAM, 2–4 vCPU |
| ОС и запас | RAM/CPU | 8 ГБ RAM, 2 vCPU |
| Диск | NVMe | 1 ТБ: модели, индекс, логи, бэкапы |

### 7.2. Профили

| Профиль | CPU | RAM | GPU | Диск | Для чего | Ориентир по цене |
|---|---|---|---:|---|---|---:|
| **Dev / пилот** | 8 vCPU | 32 ГБ | 1×RTX 4090 24 ГБ (или CPU + API) | 500 ГБ NVMe | Разработка, демо, замеры | €250–500/мес. |
| **Prod (рекомендуемый)** | 16 vCPU | 64 ГБ | 1×L40S 48 ГБ или 1×A100 40 ГБ | 1 ТБ NVMe | 32B-модель + эмбеддинги + реранкер, 1–5 тыс. запросов/день | €900–1 500/мес. |
| **Prod + HA** | 2×16 vCPU | 2×64 ГБ | 2×L40S (или 1 GPU + облачный fallback) | 2 ТБ NVMe | Отказоустойчивость, 5–20 тыс. запросов/день | €1 800–3 000/мес. |
| **Апгрейд под 70B** | 16–32 vCPU | 128 ГБ | 1×H100 80 ГБ или 2×A100 80 ГБ | 2 ТБ NVMe | Максимальное качество локально | €2 000–3 500/мес. |

Почему не CPU для LLM: 32B-модель на CPU выдаёт 2–5 токенов/с, ответ занимает минуты. Это неприемлемо для интерактивного бота. CPU достаточно для эмбеддингов запросов и реранкера, но GPU нужен для генерации.

Почему не 24 ГБ для 32B: 4-bit веса занимают ~18–20 ГБ, а KV-кэш и батчинг требуют ещё 4–8 ГБ. На 24 ГБ модель поместится, но без запаса: любой рост контекста или параллельных запросов приведёт к OOM. L40S 48 ГБ или A100 40 ГБ — безопасный минимум.

### 7.3. Ориентировочный бюджет задержки

| Этап | Время |
|---|---:|
| Эмбеддинг запроса | 10–50 мс (GPU), 50–150 мс (CPU) |
| Поиск в FAISS | 1–10 мс |
| Реранкер top-20 | 30–80 мс (GPU), 100–300 мс (CPU) |
| LLM TTFT | 300–800 мс |
| Генерация 300 токенов | 3–6 с (7B), 6–10 с (32B) |
| **Итого p95** | **5–10 с** |

Для сравнения: облачный GPT-4o-mini даёт p95 ~2–4 с. Локальный контур проигрывает в скорости, но выигрывает в конфиденциальности. Чтобы сократить задержку, используем streaming, кэш частых вопросов и маршрутизацию простых запросов на 7B.

## 8. Итоговые варианты конфигурации

### Вариант A. Полностью облачный (Cloud-first)

- LLM: GPT-4o / GPT-4o-mini.
- Эмбеддинги: text-embedding-3-large.
- Векторное хранилище: FAISS в контейнере приложения (или Chroma Cloud).
- Инфраструктура: 2 vCPU / 4 ГБ RAM, без GPU.
- Плюсы: лучший старт по качеству, минимальный ops, быстрый выход на пилот, низкая стоимость при 22 тыс. запросов/мес.
- Минусы: конфиденциальные документы покидают контур; зависимость от вендора и курса; вопросы GDPR/DPA; нельзя обрабатывать restricted-корпус.
- Стоимость: €50–350/мес. (GPT-4o-mini или GPT-4o) + ФОТ.
- Кому подходит: только если юристы разрешат передачу всего корпуса в облако (маловероятно).

### Вариант B. Полностью локальный (On-prem / private cloud)

- LLM: Qwen2.5-32B-Instruct AWQ на vLLM.
- Эмбеддинги: bge-m3.
- Векторное хранилище: FAISS.
- Инфраструктура: 16 vCPU / 64 ГБ / L40S 48 ГБ / 1 ТБ NVMe.
- Плюсы: максимальная конфиденциальность, нет платы за токены, полный контроль, работает без интернета.
- Минусы: CAPEX/OPEX на GPU, нужен MLOps, качество чуть ниже GPT-4o, latency выше, сложнее масштабировать.
- Стоимость: €900–1 500/мес. инфраструктуры + 0,2–0,3 FTE.
- Кому подходит: если весь корпус конфиденциален и облако исключено.

### Вариант C. Гибридный (рекомендуемый)

- LLM: Qwen2.5-32B-Instruct AWQ для confidential/restricted; GPT-4o-mini как fallback для public/internal (по флагу и с согласия владельца данных).
- Эмбеддинги: bge-m3 локально; text-embedding-3-large — только для сравнительной оценки на public-корпусе.
- Векторное хранилище: FAISS, отдельные индексы по доменам доступа.
- Инфраструктура: 16 vCPU / 64 ГБ / L40S 48 ГБ / 1 ТБ NVMe + небольшой app-сервер.
- Плюсы: конфиденциальность по умолчанию, возможность точечно использовать сильную облачную модель, гибкость и отсутствие lock-in, путь масштабирования.
- Минусы: сложнее маршрутизация и тестирование; две ветки качества; нужна дисциплина классификации данных.
- Стоимость: €900–1 500/мес. + €20–100/мес. API.
- Кому подходит: компании со смешанным корпусом и требованиями GDPR/SOC 2 — то есть QuantumForge.

### Вариант D. Managed RAG (облачная векторная БД + облачный LLM)

- LLM: Azure OpenAI (EU region) или OpenAI с DPA.
- Эмбеддинги: OpenAI / Azure.
- Векторное хранилище: Qdrant Cloud / Chroma Cloud / Pinecone.
- Инфраструктура: app-сервер 4 vCPU / 8 ГБ.
- Плюсы: минимум ops, эластичное масштабирование, enterprise-поддержка, быстрый старт.
- Минусы: данные в облаке, дороже при росте, vendor lock-in, меньше контроля, отдельный договор с каждым вендором.
- Стоимость: €300–900/мес. на старте (managed-кластер, поддержка, egress), растёт с объёмом и запросами.
- Кому подходит: если у компании нет GPU и MLOps, а юристы допускают EU-облако с DPA.

|---|---:|---:|---:|---:|

| Конфиденциальность (25%) | 1,0 | 5,0 | 4,5 | 3,0 |

## 9. Итоговая рекомендация

### 9.2. Почему именно FAISS (ответ на результат задания)

**Для создания бота планируется использовать FAISS.** Причина — не «потому что проще», а потому что он оптимален именно для этого кейса:

1. Корпус после чанкования — **50–100 тыс. векторов**, это малый объём. Точный поиск `FlatIP` занимает единицы миллисекунд, приближённый HNSW — доли миллисекунды. Разница с Chroma не влияет на UX.
2. **Нет отдельного сервиса** — меньше точек отказа, проще Docker Compose, бэкапы и безопасность.
3. **Полный контроль** над индексом и метаданными, что важно для аудита SOC 2 и разбора инцидентов.
4. **Локальность** — соответствует требованию не выносить конфиденциальные документы.
5. **Разграничение доступа** реализуется отдельными индексами по доменам, что проще и надёжнее, чем фильтры в общей коллекции.
6. **Путь миграции** на Qdrant/pgvector при росте — без изменения бизнес-логики.

ChromaDB остаётся в арсенале для прототипов и сравнительных экспериментов, но production-контур строится на FAISS.

### 9.3. Что закупать / арендовать

- **Сейчас (пилот):** один сервер 8 vCPU / 32 ГБ / RTX 4090 24 ГБ (или облачная GPU-машина на время замеров). Если GPU нет — пилот на GPT-4o-mini + bge-m3 на CPU, чтобы проверить качество и UX.
- **Production:** 16 vCPU / 64 ГБ / L40S 48 ГБ (A100 40 ГБ) / 1 ТБ NVMe, Ubuntu 24.04, Docker + Compose, vLLM.
- **Через 6–12 месяцев:** второй GPU-узел или H100 для 70B, Qdrant при выходе за 0,5 млн векторов, Kubernetes при тиражировании на другие команды.

### 9.4. Что проверить на пилоте перед окончательным выбором

1. **Golden set 150–200 вопросов** от четырёх ролей (разработчик, саппорт, менеджер, новичок), с эталонными источниками.
2. **Сравнение эмбеддингов:** bge-m3 vs text-embedding-3-large по Recall@5/10 и MRR.
3. **Сравнение LLM:** Qwen2.5-32B vs GPT-4o-mini vs Qwen2.5-7B по accuracy, groundedness, доле «не знаю», latency и стоимости.
4. **Сравнение векторных БД:** FAISS vs Chroma на одном и том же индексе (скорость, память, удобство фильтрации).
5. **Проверка ACL:** попытка получить restricted-документ под ролью без прав.
6. **Замер p95 latency и стоимости 1 000 запросов** в локальном и облачном контуре.

Критерии приёмки пилота:

| Метрика | Порог |
|---|---:|
| Recall@10 | ≥ 0,85 |
| Answer accuracy (LLM-as-judge + ручная выборка) | ≥ 0,80 |
| Groundedness (ответ подтверждён цитатами) | ≥ 0,90 |
| Precision режима «не знаю» | ≥ 0,85 |
| p95 latency | ≤ 10 с локально, ≤ 5 с облако |
| Утечки restricted-документов | 0 |

## 10. Риски и меры

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Утечка конфиденциальных данных через облачный fallback | Средняя | Высокое | Классификация, маршрутизация, запрет fallback для confidential/restricted, аудит |
| Галлюцинации и ложные ответы | Высокая | Высокое | Цитаты, порог релевантности, «не знаю», реранкер, evaluation |
| Единая точка отказа GPU | Средняя | Высокое | Второй узел или облачный fallback, health-checks, автоперезапуск |
| Устаревание документов | Высокая | Среднее | `updated_at`, freshness boost, владельцы документов, отчёты о пробелах |
| Плохой парсинг PDF | Высокая | Среднее | OCR, layout-aware парсеры, ручная проверка выборки |
| Рост стоимости API | Средняя | Среднее | Квоты, кэш, маршрутизация на 7B, бюджеты и алерты |
| Vendor lock-in | Средняя | Среднее | Абстракция LLM/embeddings/vector store, OpenAI-совместимый API vLLM |
| Нехватка MLOps-компетенций | Средняя | Высокое | Начать с managed-варианта D или нанять/обучить инженера |
| GDPR/DPIA | Средняя | Высокое | EU-регион, DPA, DPIA, минимизация данных, логи без PII |
| Масштабирование за пределы одного узла | Низкая (сейчас) | Среднее | Заранее заложить миграцию на Qdrant/K8s |

## Приложение A. Расчёт объёма и стоимости

**Токены:**

- 18 000 MD × ~900 токенов ≈ 16,2 млн;
- 3 000 Confluence × ~700 токенов ≈ 2,1 млн;
- 250 PDF × 40 стр. × ~600 токенов ≈ 6,0 млн;
- итого ≈ 24,3 млн токенов;
- чанк 700 токенов, перекрытие 100 → ~40–50 тыс. чанков (для расчёта индекса берём 50 тыс.).

**Индекс:**

- 50 000 × 1024 × 4 байта ≈ 205 МБ;
- + ID, метаданные, overhead ≈ 0,3–0,7 ГБ.

**API-запросы (22 тыс./мес.):**

- input: 22 000 × 3 000 = 66 млн токенов;
- output: 22 000 × 500 = 11 млн токенов;
- GPT-4o-mini: 66 × $0,15 + 11 × $0,60 ≈ $16,5/мес.;
- GPT-4o: 66 × $2,50 + 11 × $10 ≈ $275/мес.

**Индексация:**

- OpenAI small: 25 × $0,02 ≈ $0,50 однократно;
- OpenAI large: 25 × $0,13 ≈ $3,25 однократно;
- bge-m3: стоимость GPU-часов, обычно < €5 за полную переиндексацию.
