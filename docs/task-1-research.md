# Задание 1. Исследование моделей и инфраструктуры

RAG-бот для QuantumForge Software: база знаний ~21 тыс. документов (Markdown, Confluence, PDF). Нужно выбрать LLM, модель эмбеддингов, векторное хранилище и конфигурацию сервера с учётом стоимости и конфиденциальности. Цены и оценки качества — ориентировочные, подлежат проверке на пилоте.

## 1. Анализ задачи и ограничения

### 1.1. Кто пользуется ботом

| Роль | Что ищет |
|---|---|
| Разработчики | ADR, API-документацию, описание микросервисов |
| Саппорт | Решения типовых проблем пользователей |
| Менеджеры и аналитики | Регламенты и бизнес-правила |
| Новые сотрудники | Onboarding-инструкции |
| GRC / Security | Политики и доказательства для SOC 2 |

### 1.2. Объём данных

| Источник | Объём | Оценка токенов |
|---|---:|---:|
| Markdown/MDX | 18 000 файлов | ~16 млн |
| Confluence | 3 000 страниц | ~2 млн |
| PDF-спецификации | 250 документов | ~6 млн |
| **Итого** | **~21 250 документов** | **~24–26 млн** |
| Прирост | 400 страниц/мес. | ~0,5 млн/мес. |

При чанковании 600–800 токенов с перекрытием 10–15% — **~40–55 тыс. чанков** на старте, ~700 чанков/мес. прироста. С учётом версий и дублей систему проектируем на **100–200 тыс. векторов**. Индекс на 1024 измерения занимает 0,3–0,7 ГБ на 50 тыс. векторов — помещается в RAM одного сервера.

### 1.3. Ограничения

- **Конфиденциальность.** Terraform state, ADR, клиентские данные, политики SOC 2 и HR-документы нельзя бесконтрольно выносить в облако. Компания работает в ЕС, поэтому YandexGPT и GigaChat с размещением данных в РФ не подходят.
- **Классификация данных.** Public/internal могут обрабатываться в облаке; confidential/restricted — только локально, в отдельных индексах с ACL.
- **Языки и качество.** Русский и английский, обязательные ссылки на источники, честный ответ «я не знаю», разграничение доступа.
- **Нагрузка.** 1 000 запросов в день (22 тыс./мес.), ~3 000 входных и ~500 выходных токенов на запрос.
- **Задержка.** p95 ≤ 8–10 с локально, ≤ 5 с в облаке.

## 2. Сравнение LLM

| Модель | Качество (RU/EN/код) | Скорость | Стоимость при 22 тыс. запросов/мес. | Развёртывание | Конфиденциальность |
|---|---|---|---|---|---|
| GPT-4o | 4,5 / 5,0 / 4,5 | 60–100 ток./с | ~$275 | API, ★☆☆☆☆ | Данные уходят вендору |
| GPT-4o-mini | 4,0 / 4,5 / 4,0 | 80–120 ток./с | ~$17 | API, ★☆☆☆☆ | Данные уходят вендору |
| YandexGPT Pro | 4,5 / 3,5 / 3,5 | 30–60 ток./с | Сопоставимо, уточнять | API, ★★☆☆☆ | Данные в РФ |
| Qwen2.5-32B-Instruct | 4,5 / 4,5 / 4,5 | 35–60 ток./с | €750–1 300 (GPU) | vLLM, ★★★☆☆ | Полностью локально |
| Llama 3.3 70B | 4,0 / 4,5 / 4,0 | 20–35 ток./с | €1 900–3 150 | 2×GPU, ★★★★☆ | Полностью локально |
| Qwen2.5-7B | 3,5 / 3,5 / 3,5 | 90–140 ток./с | €330–560 | Ollama/vLLM, ★★☆☆☆ | Полностью локально |

**Качество.** GPT-4o — эталон, но дорог и выносит данные. Qwen2.5-32B близок к нему на RU/EN и коде, хорошо держит формат ответа с цитатами. YandexGPT силён на русском, но слабее на английском и в коде. Llama 3.3 70B качественнее 32B, но требует 1×H100 или 2×A100.

**Скорость.** Облачные модели дают 60–120 ток./с и TTFT 0,2–0,8 с. Локальная 32B — 35–60 ток./с, 70B — 20–35 ток./с. Для простых FAQ используем 7B, для сложных вопросов — 32B.

**Стоимость.** При текущей нагрузке облачный GPT-4o-mini дешевле локального GPU в десятки раз. Локальный контур оправдан не экономией на токенах, а конфиденциальностью и возможностью обрабатывать restricted-документы. В TCO локального варианта нужно учитывать 0,2–0,3 FTE на MLOps.

**Развёртывание.** API — ключ и SDK. Локально — GPU, vLLM, квантование, мониторинг; для 70B сложность выше.

**Вывод:** для confidential/restricted — локальная **Qwen2.5-32B-Instruct AWQ**; для public/internal — допустим **GPT-4o-mini** как fallback. YandexGPT/GigaChat не подходят из-за юрисдикции РФ. Llama 3.3 70B — кандидат на второй этап.

## 3. Сравнение моделей эмбеддингов

| Модель | Размерность / контекст | Индексация 50 тыс. чанков | Качество (RU/EN/код) | Стоимость | Конфиденциальность |
|---|---|---|---:|---|---|
| BAAI/bge-m3 | 1024 / 8 192 | 10–30 мин GPU, 6–12 ч CPU | 4,5 / 4,5 / 4,5 | ~€0 | Локально |
| multilingual-e5-large | 1024 / 512 | 8–25 мин GPU | 4,5 / 4,0 / 4,0 | ~€0 | Локально |
| OpenAI text-embedding-3-small | 1536 / 8 191 | 30–60 мин (API) | 4,0 / 4,5 / 4,0 | ~$0,50 за корпус | Данные уходят |
| OpenAI text-embedding-3-large | 3072 / 8 191 | 40–90 мин (API) | 4,5 / 5,0 / 4,5 | ~$3,25 за корпус | Данные уходят |
| Yandex embeddings | — | 30–90 мин (API) | 4,5 / 3,5 / 3,0 | Уточнять | Данные в РФ |

**Скорость индексации.** На GPU bge-m3 обрабатывает корпус за 10–30 минут; на CPU — за 6–12 часов, что приемлемо для ночной переиндексации. Инкрементальная индексация ~700 новых чанков занимает секунды на GPU.

**Качество.** bge-m3 — лучший открытый мультиязычный вариант: RU/EN, код, 8k контекст, поддержка dense + sparse для гибридного поиска. text-embedding-3-large немного сильнее в английском, но данные уходят в облако. e5-large — запасной локальный вариант.

**Стоимость.** Эмбеддинги стоят единицы долларов даже в облаке и не являются решающим фактором. Выбор определяется качеством на корпусе и конфиденциальностью.

**Вывод:** **BAAI/bge-m3**. text-embedding-3-large — только для сравнительной оценки на public-корпусе. Yandex embeddings не используем из-за юрисдикции.

## 4. Сравнение FAISS и ChromaDB

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска top-10 (50–100 тыс. векторов) | Flat: 3–10 мс; HNSW: < 1 мс | Embedded: 2–5 мс; server: 5–15 мс |
| Скорость индексации 50 тыс. | 1–5 с (Flat), 10–60 с (HNSW) | 30–120 с |
| Сложность внедрения | Библиотека в приложении; нужен свой слой метаданных и ACL | Проще «из коробки»; в server-режиме добавляет отдельный сервис |
| Удобство работы | Полный контроль, воспроизводимость, тонкая настройка индекса | Встроенные метаданные, `where`-фильтры, CRUD, документы |
| Метаданные и ACL | Хранить отдельно; ACL — отдельные индексы по доменам | Встроены; фильтрация `where` |
| CRUD и персистентность | Ограниченный CRUD; индекс — файл, бэкап вручную | add/update/delete; SQLite + сегменты |
| Масштабирование и HA | Нет распределённого режима и HA | OSS — один узел, HA нет; Chroma Cloud — платно |
| Стоимость владения | Бесплатно; затраты — разработка обвязки | Бесплатно; затраты — эксплуатация ещё одного сервиса |

**Скорость.** Оба варианта укладываются в требования. Разница в единицы миллисекунд не влияет на UX, потому что основное время тратит LLM.

**Сложность и удобство.** ChromaDB быстрее для прототипа: коллекции, метаданные и фильтры уже есть. FAISS требует самостоятельно реализовать слой метаданных, но даёт полный контроль и не добавляет сервис.

**Стоимость.** Оба бесплатны. FAISS «платит» сложностью разработки, ChromaDB — эксплуатацией сервиса, бэкапами и обновлениями.

**Вывод: выбираем FAISS.** На объёме 50–100 тыс. чанков он даёт точный поиск за миллисекунды, не требует отдельного сервера и полностью локален. ACL реализуем отдельными индексами по доменам доступа (engineering, support, business/GRC, onboarding/HR), метаданные храним в PostgreSQL. ChromaDB — для прототипов и сравнительных экспериментов. При росте до 0,5–1 млн векторов или необходимости real-time ACL и мультитенантности — миграция на Qdrant.

## 5. Конфигурация сервера

| Профиль | CPU | RAM | GPU | Диск | Назначение | Ориентир по цене |
|---|---|---|---|---|---:|---:|
| Dev / пилот | 8 vCPU | 32 ГБ | 1×RTX 4090 24 ГБ | 500 ГБ NVMe | Разработка, демо, замеры | €250–500/мес. |
| **Prod** | **16 vCPU** | **64 ГБ** | **1×L40S 48 ГБ или A100 40 ГБ** | **1 ТБ NVMe** | 32B + эмбеддинги + реранкер, 1–5 тыс. запросов/день | €900–1 500/мес. |
| Prod + HA | 2×16 vCPU | 2×64 ГБ | 2×L40S | 2 ТБ NVMe | Отказоустойчивость, 5–20 тыс. запросов/день | €1 800–3 000/мес. |
| Апгрейд под 70B | 16–32 vCPU | 128 ГБ | 1×H100 80 ГБ | 2 ТБ NVMe | Максимальное качество локально | €2 000–3 500/мес. |

Почему так:

- 32B-модель в 4-bit занимает ~18–20 ГБ VRAM, ещё 4–8 ГБ нужны под KV-кэш. 24 ГБ — впритык, 40–48 ГБ — безопасный минимум.
- Индекс FAISS на 100 тыс. векторов занимает менее 1 ГБ RAM.
- CPU-инференс 32B даёт 2–5 ток./с, поэтому для генерации нужен GPU. CPU достаточно для эмбеддингов запросов и реранкера.

## 6. Варианты конфигурации и выбор

| Вариант | Состав | Плюсы | Минусы | €/мес. |
|---|---|---|---|---|
| A. Cloud-first | GPT-4o + OpenAI embeddings + FAISS | Лучшее качество, минимум ops | Данные вне контура, GDPR | 50–350 |
| B. Local-first | Qwen2.5-32B + bge-m3 + FAISS, свой GPU | Полная конфиденциальность | Дорого, нужен MLOps, latency выше | 900–1 500 + FTE |
| **C. Hybrid** | Локальные Qwen2.5-32B + bge-m3 + FAISS; GPT-4o-mini только для public/internal | Баланс приватности, качества и гибкости | Сложнее маршрутизация | 900–1 500 + API |
| D. Managed RAG | Azure OpenAI (EU) + Qdrant/Chroma Cloud | Минимум ops, масштабируемость | Данные в облаке, lock-in | 300–900 |

| Критерий (вес) | A. Cloud | B. Local | C. Hybrid | D. Managed |
|---|---:|---:|---:|---:|
| Качество (30%) | 5,0 | 4,0 | 4,5 | 5,0 |
| Конфиденциальность (25%) | 1,0 | 5,0 | 4,5 | 3,0 |
| TCO (20%) | 4,0 | 3,0 | 3,5 | 2,5 |
| Простота (15%) | 5,0 | 2,0 | 3,0 | 4,5 |
| Масштабируемость (10%) | 5,0 | 3,0 | 4,0 | 5,0 |
| **Итог** | **3,80** | **3,65** | **4,03** | **3,93** |

**Рекомендация — вариант C (гибридный).** Он закрывает конфиденциальность на уровне локального варианта и сохраняет гибкость облака. D — fallback, если нет GPU и MLOps, а юристы допускают EU-облако.

## 7. Итоговая рекомендация

| Слой | Выбор |
|---|---|
| LLM | Qwen2.5-32B-Instruct AWQ на vLLM; GPT-4o-mini для public/internal |
| Эмбеддинги | BAAI/bge-m3 |
| Векторная БД | **FAISS** (`IndexIDMap2` + `IndexFlatIP`, отдельные индексы по доменам) |
| Реранкер | bge-reranker-v2-m3 |
| Сервер | 16 vCPU / 64 ГБ RAM / 1×L40S 48 ГБ / 1 ТБ NVMe |

**Векторная БД — FAISS**, потому что корпус (~50–100 тыс. чанков) мал для распределённой БД, точный поиск занимает миллисекунды, не нужен отдельный сервис, всё работает локально и соответствует требованиям конфиденциальности. Разграничение доступа реализуется отдельными индексами по доменам. ChromaDB удобнее для прототипа, но в production добавляет сервис без выигрыша на нашем объёме; при росте — переход на Qdrant.
