# Задание 1. Исследование моделей и инфраструктуры

RAG-бот для QuantumForge Software: база знаний — 18 000 Markdown/MDX, 3 000 страниц Confluence и 250 PDF-спецификаций. Нужно выбрать LLM, модель эмбеддингов, векторное хранилище и конфигурацию сервера с учётом стоимости и конфиденциальности.

Точные параметры нагрузки и требования к latency в брифе не заданы — это предмет замера на пилоте. Ниже сравниваются технические характеристики, стоимость и ограничения, которые влияют на выбор стека.

## 1. Анализ задачи и ограничения

### 1.1. Кто пользуется ботом

| Роль | Что ищет |
|---|---|
| Разработчики | ADR, API-документацию, описание микросервисов |
| Саппорт | Решения типовых проблем пользователей |
| Менеджеры и аналитики | Регламенты и бизнес-правила |
| Новые сотрудники | Onboarding-инструкции |
| GRC / Security | Политики и доказательства для SOC 2 |

### 1.2. Данные

| Источник | Объём | Где лежит |
|---|---:|---|
| Markdown/MDX | 18 000 файлов | Репозитории GitHub |
| Confluence | 3 000 страниц | 30 пространств |
| PDF-спецификации | 250 документов | Наследие заказных проектов |
| Прирост | ~400 страниц/мес. | Confluence, репозитории |

Точное число токенов и чанков зависит от парсинга, чанкования и дедупликации. Для выбора архитектуры важно, что корпус измеряется десятками тысяч документов, а не миллионами: он не требует распределённой векторной БД и помещается на один узел.

### 1.3. Ограничения

- **Конфиденциальность.** Terraform state, Helm charts, ADR, клиентские данные, политики SOC 2 и внутренние регламенты нельзя бесконтрольно выносить в облако. Компания работает в ЕС, поэтому YandexGPT с размещением данных в РФ не подходит.
- **Классификация данных.** Public/internal могут обрабатываться в облаке; confidential/restricted — только локально, в отдельных индексах с ACL.
- **Языки и качество.** Русский и английский, обязательные ссылки на источники, честный ответ «я не знаю», разграничение доступа по ролям.

## 2. Сравнение LLM

| Модель | Качество | Скорость | Стоимость | Развёртывание | Конфиденциальность |
|---|---|---|---|---|---|
| GPT-4o | Эталонное: лучшее следование инструкциям | 60–100 ток./с | $2,50 / $10 за 1 млн входных/выходных токенов | Простой API | Данные уходят вендору |
| GPT-4o-mini | Высокое, немного уступает GPT-4o | 80–120 ток./с | $0,15 / $0,60 за 1 млн токенов | Простой API | Данные уходят вендору |
| YandexGPT Pro | Сильный русский, слабее EN и код | 30–60 ток./с | Тарифы Yandex Cloud, уточнять | Простой API, аккаунт в РФ | Данные в РФ |
| Qwen2.5-32B-Instruct | Высокое на RU/EN и коде, близко к GPT-4o | 35–60 ток./с | GPU-сервер, ориентир €700–1 200/мес. | Средний: vLLM, квантование | Полностью локально |
| Llama 3.3 70B | Высокое, особенно EN; тяжелее в эксплуатации | 20–35 ток./с | 1×H100 или 2×A100, ориентир €1 800–3 000/мес. | Сложный: 2×GPU | Полностью локально |
| Qwen2.5-7B | Базовое: для простых FAQ и маршрутизации | 90–140 ток./с | RTX 4090, ориентир €300–500/мес. | Средний: Ollama/vLLM | Полностью локально |

**Качество.** GPT-4o — эталон, но дорог и выносит данные. Qwen2.5-32B близок к нему на RU/EN и коде, хорошо держит формат ответа с цитатами. YandexGPT силён на русском, но слабее на английском и в коде. Llama 3.3 70B качественнее 32B, но требует 1×H100 или 2×A100.

**Скорость.** Облачные модели дают 60–120 ток./с и TTFT 0,2–0,8 с. Локальная 32B — 35–60 ток./с, 70B — 20–35 ток./с. Для простых FAQ можно использовать 7B, для сложных вопросов — 32B.

**Стоимость.** У облачных моделей оплата за токены, у локальных — фиксированная стоимость GPU-сервера независимо от числа запросов. При малых объёмах API дешевле; при постоянной нагрузке и запрете выносить данные локальный GPU выгоднее по совокупности рисков и затрат. В TCO локального варианта нужно учитывать электроэнергию и трудозатраты на MLOps.

**Развёртывание.** API — ключ и SDK. Локально — GPU, vLLM, квантование, мониторинг; для 70B сложность выше.

**Вывод:** для confidential/restricted — локальная **Qwen2.5-32B-Instruct AWQ**; для public/internal — допустим **GPT-4o-mini** как fallback. YandexGPT не подходит из-за юрисдикции РФ. Llama 3.3 70B — кандидат на второй этап.

## 3. Сравнение моделей эмбеддингов

| Модель | Размерность / контекст | Скорость индексации | Качество | Стоимость | Конфиденциальность |
|---|---|---|---|---|---|
| BAAI/bge-m3 | 1024 / 8 192 | GPU — минуты на десятки тысяч чанков; CPU — часы | Сильное на RU/EN и коде; dense + sparse | ~€0 (свой GPU) | Локально |
| multilingual-e5-large | 1024 / 512 | GPU — минуты; CPU — часы | Сильное на RU, слабее EN и код | ~€0 (свой GPU) | Локально |
| OpenAI text-embedding-3-small | 1536 / 8 191 | Зависит от лимитов API | Хорошее EN, среднее RU | $0,02 за 1 млн токенов | Данные уходят |
| OpenAI text-embedding-3-large | 3072 / 8 191 | Медленнее small | Очень сильное EN, хорошее RU | $0,13 за 1 млн токенов | Данные уходят |
| Yandex embeddings | — | Зависит от лимитов API | Сильное RU, слабее EN и код | Тарифы Yandex Cloud | Данные в РФ |

**Скорость индексации.** На GPU bge-m3 и e5-large обрабатывают десятки тысяч чанков за минуты; на CPU — за часы, что приемлемо для ночной переиндексации. У облачных моделей скорость ограничена rate limit API.

**Качество.** bge-m3 — лучший открытый мультиязычный вариант: RU/EN, код, 8k контекст, поддержка dense + sparse для гибридного поиска. text-embedding-3-large немного сильнее в английском, но данные уходят в облако. e5-large — запасной локальный вариант.

**Стоимость.** Эмбеддинги стоят центы за миллион токенов даже в облаке и не являются решающим фактором. Выбор определяется качеством на корпусе и конфиденциальностью.

**Вывод:** **BAAI/bge-m3**. text-embedding-3-large — только для сравнительной оценки на public-корпусе. Yandex embeddings не используем из-за юрисдикции.

## 4. Сравнение FAISS и ChromaDB

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска top-10 | Flat: 3–10 мс; HNSW: < 1 мс | Embedded: 2–5 мс; server: 5–15 мс |
| Скорость индексации | Секунды-минуты в зависимости от типа индекса | Десятки секунд-минуты |
| Сложность внедрения | Библиотека в приложении; нужен свой слой метаданных и ACL | Проще «из коробки»; в server-режиме добавляет отдельный сервис |
| Удобство работы | Полный контроль, воспроизводимость, тонкая настройка индекса | Встроенные метаданные, `where`-фильтры, CRUD, документы |
| Метаданные и ACL | Хранить отдельно; ACL — отдельные индексы по доменам | Встроены; фильтрация `where` |
| CRUD и персистентность | Ограниченный CRUD; индекс — файл, бэкап вручную | add/update/delete; SQLite + сегменты |
| Масштабирование и HA | Нет распределённого режима и HA | OSS — один узел, HA нет; Chroma Cloud — платно |
| Стоимость владения | Бесплатно; затраты — разработка обвязки | Бесплатно; затраты — эксплуатация ещё одного сервиса |

**Скорость.** Оба варианта укладываются в требования для корпуса такого масштаба. Разница в единицы миллисекунд не влияет на UX, потому что основное время тратит LLM.

**Сложность и удобство.** ChromaDB быстрее для прототипа: коллекции, метаданные и фильтры уже есть. FAISS требует самостоятельно реализовать слой метаданных, но даёт полный контроль и не добавляет сервис.

**Стоимость.** Оба бесплатны. FAISS «платит» сложностью разработки, ChromaDB — эксплуатацией сервиса, бэкапами и обновлениями.

**Вывод: выбираем FAISS.** Для корпуса из 21 тыс. документов он даёт точный поиск за миллисекунды, не требует отдельного сервера и полностью локален. ACL реализуем отдельными индексами по доменам доступа (engineering, support, business/GRC, onboarding/HR), метаданные храним в PostgreSQL. ChromaDB — для прототипов и сравнительных экспериментов. При росте до миллионов векторов или необходимости real-time ACL и мультитенантности — миграция на Qdrant.

## 5. Конфигурация сервера

| Профиль | CPU | RAM | GPU | Диск | Назначение |
|---|---|---|---|---|---|
| Dev / пилот | 8 vCPU | 32 ГБ | 1×RTX 4090 24 ГБ | 500 ГБ NVMe | Разработка, демо, замеры |
| **Prod** | **16 vCPU** | **64 ГБ** | **1×L40S 48 ГБ или A100 40 ГБ** | **1 ТБ NVMe** | 32B + эмбеддинги + реранкер |
| Prod + HA | 2×16 vCPU | 2×64 ГБ | 2×L40S | 2 ТБ NVMe | Отказоустойчивость |
| Апгрейд под 70B | 16–32 vCPU | 128 ГБ | 1×H100 80 ГБ | 2 ТБ NVMe | Максимальное качество локально |

Почему так:

- 32B-модель в 4-bit занимает ~18–20 ГБ VRAM, ещё 4–8 ГБ нужны под KV-кэш. 24 ГБ — впритык, 40–48 ГБ — безопасный минимум.
- Индекс FAISS для корпуса такого масштаба занимает единицы гигабайт и помещается в RAM.
- CPU-инференс 32B даёт 2–5 ток./с, поэтому для генерации нужен GPU. CPU достаточно для эмбеддингов запросов и реранкера.

## 6. Варианты конфигурации и выбор

| Вариант | Состав | Сильные стороны | Ограничения | Стоимость |
|---|---|---|---|---|
| A. Cloud-first | GPT-4o + OpenAI embeddings + FAISS | Лучшее качество, минимум ops | Все данные, включая confidential, уходят в облако; GDPR | Оплата за токены + хостинг |
| B. Local-first | Qwen2.5-32B + bge-m3 + FAISS, свой GPU | Полная конфиденциальность | Дорого, нужен MLOps, нет облачного fallback | GPU-сервер + MLOps |
| **C. Hybrid** | Локальные Qwen2.5-32B + bge-m3 + FAISS; GPT-4o-mini только для public/internal | Приватность по умолчанию + гибкость облака | Сложнее маршрутизация и классификация данных | GPU + небольшие расходы на API |
| D. Managed RAG | Azure OpenAI (EU) + Qdrant/Chroma Cloud | Минимум ops, масштабируемость | Знания хранятся у вендоров, lock-in | Подписка managed-сервисов + токены |

**Почему C:**

- **Конфиденциальность.** Confidential/restricted обрабатываются только локально. В A и D они уходят в облако, в B всё локально, но нет гибкости для public/internal.
- **Качество.** Локальная Qwen2.5-32B закрывает основные сценарии; для несложных public/internal-запросов можно использовать GPT-4o-mini.
- **Стоимость.** C близок к B по инфраструктуре, но добавляет лишь небольшие расходы на API; D дороже за счёт managed-подписок, A дешевле, но не проходит по конфиденциальности.
- **Эксплуатация.** C сложнее A и D из-за маршрутизации, но проще B, потому что часть трафика можно отдать облаку.

A отклонён, потому что не обеспечивает конфиденциальность. B отклонён как избыточный по стоимости и ops при наличии public/internal-трафика. D отклонён из-за хранения знаний у вендоров и lock-in. **Рекомендация — C.**

## 7. Итоговая рекомендация

| Слой | Выбор |
|---|---|
| LLM | Qwen2.5-32B-Instruct AWQ на vLLM; GPT-4o-mini для public/internal |
| Эмбеддинги | BAAI/bge-m3 |
| Векторная БД | **FAISS** (`IndexIDMap2` + `IndexFlatIP`, отдельные индексы по доменам) |
| Реранкер | bge-reranker-v2-m3 |
| Сервер | 16 vCPU / 64 ГБ RAM / 1×L40S 48 ГБ / 1 ТБ NVMe |

**Векторная БД — FAISS**, потому что корпус из 21 тыс. документов не требует распределённой БД, точный поиск занимает миллисекунды, не нужен отдельный сервис, всё работает локально и соответствует требованиям конфиденциальности. Разграничение доступа реализуется отдельными индексами по доменам. ChromaDB удобнее для прототипа, но в production добавляет сервис без выигрыша на этом объёме; при росте — переход на Qdrant.
